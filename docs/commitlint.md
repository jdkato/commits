# From commitlint

commitlint reads a message with a parser, then runs each rule of a shareable
config against the parts. Here the View is the parser, and each rule is a
Vale rule with the same name in CamelCase, under `Commitlint`, with the
rules `config-conventional` turns on turned on, and the rest off as they are
there.

## Config

```js
// commitlint.config.js
export default { extends: ["@commitlint/config-conventional"] };
```

becomes

```ini
[COMMIT_EDITMSG]
BasedOnStyles = Commits, Conventional, Commitlint
```

and the hook, from `commitlint --edit "$1"` to
`vale --path=COMMIT_EDITMSG < "$1"`. Messages commitlint ignores by default,
merges, reverts, and `fixup!`, are let through by
[`script/commit-msg`](../script/commit-msg) the same way. A rule's level
is set as it is for any Vale rule, and a value with the bracket key:

```ini
Commitlint.HeaderLength[max] = 72
Commitlint.Type = NO
```

## Every rule

`config-conventional` turns these on, at the level given:

| commitlint | Level | Here |
| ---------- | ----- | ---- |
| `type-empty` | error | `Conventional.Type` |
| `type-enum` | error | `Commitlint.Type` |
| `type-case` | error | `Commitlint.TypeCase` |
| `subject-empty` | error | `Conventional.Description` |
| `subject-case` | error | `Commitlint.SubjectCase` |
| `subject-full-stop` | error | `Commitlint.FullStop` |
| `header-max-length` | error | `Commitlint.HeaderLength`, `[max]` |
| `header-trim` | error | `Commits.Whitespace` |
| `body-leading-blank` | warning | `Commits.Blank`, as an error: Git reads a body on the second line as part of the subject |
| `body-max-line-length` | error | `Commitlint.BodyLength` |
| `footer-leading-blank` | warning | `Conventional.Footer` |
| `footer-max-line-length` | error | `Commitlint.FooterLength` |

The rest of the [reference](https://commitlint.js.org/reference/rules.html)
is here and off; turn one on with `= YES`, and set its value with the
bracket key where the rule takes one:

| commitlint | Here | Value |
| ---------- | ---- | ----- |
| `scope-enum` | `Commitlint.Scope` | Extend it with your list, as with a type; the shipped list is a placeholder |
| `scope-empty: never` | `Commitlint.ScopeRequired` | |
| `scope-case: lower-case` | `Commitlint.ScopeCase` | Another case: extend with `raw` rewritten |
| `scope-max-length`, `scope-min-length` | `Commitlint.ScopeLength` | `[max]`, `[min]` |
| `scope-delimiter-style` | `Commitlint.ScopeDelimiter` | A scope that mixes `/` and `,` |
| `header-case: lower-case` | `Commitlint.HeaderCase` | |
| `header-full-stop` | `Commitlint.FullStop` | The same check in practice |
| `header-min-length` | `Commitlint.HeaderMinLength` | `[min]` |
| `subject-max-length`, `subject-min-length` | `Commitlint.SubjectLength` | `[max]`, `[min]` |
| `subject-exclamation-mark: never` | `Commitlint.Exclamation` | |
| `type-max-length`, `type-min-length` | `Commitlint.TypeLength` | `[max]`, `[min]`; a type list bounds it already |
| `body-empty: never` | `Commitlint.Body` | |
| `body-min-length` | `Commitlint.BodyMinLength` | `[min]` |
| `body-max-length` | `Commitlint.BodyMaxLength` | `[max]` |
| `body-case: lower-case` | `Commitlint.BodyCase` | Another case: extend with `raw` rewritten |
| `body-full-stop: never` | `Commitlint.BodyFullStop` | |
| `footer-empty: never` | `Commitlint.FooterRequired` | |

`Exclamation` and `BreakingBang` pull opposite ways, as their originals do;
turn on one.

## Differences

`subject-case` in commitlint compares the whole subject to four case
styles; here a subject that opens with a capitalized word, or is in capitals
throughout, is what fails, which passes and fails the same messages in
practice.

The parser is a different one. commitlint's reads the header with one
regex and takes everything after a note keyword or a reference as footer;
the View takes a trailer block to be a paragraph that opens with a `Token:
value` line and runs to the next blank line, which is the spec's reading.
A `Fixes #12` on the line after the body is a footer to commitlint and a
body line here, which `Conventional.Footer` reports.

`Upstream.test.yml` beside the style holds config-conventional's own test
messages with their verdicts, generated by `script/upstream.py`, and the
rules here agree with every one.

Shareable configs, plugins, and the prompt have no counterpart. A shared
config is a style: put your rules in a repository, zip it, and name it under
`Packages`, and every project syncs it. A plugin is a rule. The prompt is
commitizen's or gitmoji-cli's job.

What you gain is the rest of Vale. `Vale.Spelling` reads the message with
the body parsed as Markdown, so an identifier in backticks is skipped and a
misspelling in prose is not. Any rule you already run on the docs runs on
the log with a line in the config. And a run is a tenth of the time:
[comparison.md](comparison.md).
